# mock_框架验证_API

This directory contains comprehensive documentation for the Mock Framework Verification API, specifically designed for the Cangjie programming language. It covers essential unit testing concepts including behavior verification, mock objects, spy objects, and assertion patterns. The resources detail how to use the `Verify` class, verification blocks, and expectation APIs to validate method call counts, parameters, and execution order. Suitable for developers and QA engineers who need to implement robust unit tests, debug mock interactions, and ensure external dependencies behave as expected within their Cangjie applications.

## Detailed Description

### mock_框架验证_API_3more.md
This document serves as a technical reference for the Verification API within a mock framework, explaining how to assert method call behaviors during unit testing. It covers the core functionality of verifying call occurrences, counts, parameters, and order, utilizing the Verify class and the @Called macro to construct verification statements and blocks. Key information includes the use of parameter matchers and cardinality functions such as once(), atLeastOnce(), and times() to define expected invocation frequencies based on execution logs. Targeted at developers using the Cangjie language, this guide assumes familiarity with mock objects and stub signatures to effectively implement test assertions.

### 其他_API_3more.md
This document serves as API reference documentation for the Verify class within a mocking framework, detailing utility methods and error handling. It covers utility functions like that, noInteractions, and clearInvocationLog, provides the complete class API signature, and explains verification failure types. Key takeaways include understanding how to reset invocation logs, verify no interactions, and interpret specific errors like disjoint statements or unexpected calls which throw VerificationFailedException. The target audience is developers writing unit tests who need to validate mock object behavior and debug verification failures.

### 示例和模式.md
This document serves as a practical tutorial for the Cangjie language's unit testing mock API, demonstrating common patterns for verifying interactions between test code and external objects. It covers three main verification scenarios: verifying the number of method calls, verifying calls with specific arguments or complex conditions, and verifying the strict order of method invocations. Key takeaways include creating spy and mock objects, using verification blocks like Verify.unordered and Verify.ordered, and handling argument matching with ofType or custom matchers. The guide also distinguishes between Partial and Exhaustive verification modes. This resource targets developers familiar with unit testing concepts who need to implement behavior verification in Cangjie.

### 预期与验证_API.md
This document serves as a technical guide for using Expectation and Verification APIs within a mocking framework to manage test assertions. It covers two primary approaches: explicit verification using `Verify.that` or `Verify.unordered` to validate call counts and arguments, versus defining expectations directly on stubs using `.once()`. Key information includes the recommendation to avoid duplicating configuration steps and to choose the approach that best reflects the test's intent. The text highlights that expectations automatically fail tests if stubs are not triggered, whereas verification blocks allow for granular checks. This guide is intended for developers writing unit tests who require precise control over mock object behavior and validation.

### 验证块.md
This technical guide explains the usage and behavior of verification blocks within a mocking framework for the Cangjie programming language. It details two primary verification modes: "Ordered" for checking exact call sequences and "Unordered" for verifying call frequencies. It also covers dynamic block construction using lambdas. Key concepts include immediate validation, independent block execution, and cardinality specifiers like `once()` or `atLeastOnce()`. Ordered verification requires listing all relevant calls, while Unordered supports both "Exhaustive" and "Partial" modes to handle unlisted interactions. Targeted at developers writing unit tests who need to assert mock object interactions.

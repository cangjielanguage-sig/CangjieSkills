# 应用加密

This directory provides comprehensive documentation on application encryption, with a specific focus on the HarmonyOS ecosystem. It details system-level security mechanisms designed to safeguard code assets against reverse engineering and unauthorized access. Key topics include the technical implementation of AES encryption for end-to-end protection, the impact of encryption on application performance and package size, and best practices for combining encryption with obfuscation. The documentation also addresses common developer concerns regarding file type support (such as .abc and .so files) and the operational workflow for enabling encryption during the app market upload process. Furthermore, it explores alternative protection strategies and the necessity of supplementary security measures. This resource is essential for HarmonyOS developers and security engineers aiming to maximize application security while managing performance trade-offs.

## Detailed Description

### 常见问题.md 常见问题.md
This document serves as a FAQ guide addressing common concerns regarding application code encryption and asset protection strategies. It covers three main topics: the necessity of supplementary security measures alongside official encryption, alternative protection methods if encryption is not utilized, and the impact of encryption on application performance and package size. Key takeaways emphasize that while encryption raises the barrier against reverse engineering, it should be combined with obfuscation and third-party hardening for optimal security. Users should anticipate minor performance overhead and increased app volume when enabling encryption. This reference guide targets application developers and security engineers seeking to safeguard their code assets. Keywords: code encryption, obfuscation, reverse engineering, app security, performance impact.

### 应用加密_5more.md 应用加密_5more.md
This document outlines the HarmonyOS application encryption feature, a system-level security mechanism designed to protect code against reverse engineering. It covers the feature's introduction, performance impacts, encryption effects on specific file types like .abc, and the usage process. Key takeaways include the use of AES encryption for end-to-end protection, where code remains encrypted on disk and is only decrypted in memory during execution. The process is transparent to developers during coding but requires selection during the app market upload phase. This guide targets HarmonyOS developers seeking to enhance app security, noting that .so files are currently unencrypted and support is primarily for phones and tablets, with potential performance overheads related to file size.
